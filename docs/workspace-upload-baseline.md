# 工作区上传基线

这个入口回答一个问题：只改一个小文件，当前 Worker 实际向平台上传多少字节？它使用真实 AgentMoor `sync`/`restore` CLI 和本机平台，不调用模型、不读取用户工作区，也不实现增量格式。INT-64 仍待完成。

先提交源码并构建，再把结果写到仓库之外，保证结果能对应确切的源码和二进制：

```sh
make build
python3 tests/workspace_upload_baseline.py --files 8 --bytes 127 --seed 0 --output /tmp/workspace-small.json
python3 tests/workspace_upload_baseline.py --files 5000 --bytes 4096 --seed 0 --output /tmp/workspace-5000.json
```

需要 Go、Python 3.11+，以及允许绑定本机回环端口。脚本检查源码已提交、二进制内的 VCS 提交与当前提交一致。可以调整 `--files`、每个文件的 `--bytes` 和 `--seed`；生成量最多为 512 MiB。此入口不进入普通 CI，避免增加每次提交的耗时。

每次在独占临时目录生成合成文件，平台目录、凭据、配置和 Worker 游标都在工作区之外。只继承明确允许的环境变量，防止误用本机的数据库、对象存储或模型配置。平台和透明转发代理都只监听 `127.0.0.1`；退出时关闭服务并清理临时数据。输出不包含 token。

四个测量阶段依次为首次同步、完全不变、修改一个同尺寸文件、删除一个文件。代理逐块转发请求，记录真实 `PUT /v1/changes/*/content` 请求体字节和次数，统计不含 HTTP 头及连接开销。每阶段时间只覆盖真实 `sync` CLI，包括扫描、打包和上传；生成文件及后续正确性检查不在阶段时间内。结果另有全流程耗时。

测量同时核对：无变化阶段零上传；两个变更阶段仍上传完整 `workspace-tar.v1`；三个固定版本下载后的摘要、长度和全部文件内容正确；修改和删除后，CLI 仍能把 v1 恢复到新目录，所有原文件摘要不变。业务验算只通过公开 HTTP 和真实恢复命令完成，不读取平台数据库。

JSON 保存源码提交、二进制 SHA-256、Go/Python/系统版本、存储类型、每阶段源文件数量/字节、格式、固定版本摘要、上传量和耗时。这是特定机器上的合成基线，不是生产性能保证。后续增量方案应与同样输入比较，不能把“整个工作区重新上传”表述为“只传变化文件”。

## 2026-11-26 实测

程序和平台二进制均来自已提交的 `0da7be8a5133d91601f4b334ed2a707a72614ce1`，二进制内 VCS 状态为干净。macOS 27.2.1 ARM64、Go 1.27.4、Python 3.15.2，SQLite 与本地对象存储，seed 为 0。下面是逐个顺序运行的单次样本，机器没有专门隔离其他负载；这些耗时不是生产承诺。

## 后续增量方案的边界

优先保留公开 workspace 内容接口的完整 tar 行为，在内部引入文件对象和 manifest，由服务端按固定版本组装 tar。这样旧下载校验和恢复约定可以保留，Worker 上传只传变化对象；仍需补齐内部引用、原子提交、GC 和组装成本的验收，当前没有实现。

另一种方案让公开内容成为 manifest、由客户端按需下载文件，可减少局部读取量，但会要求客户端理解新格式、新内容端点和引用规则。现有需求是完整恢复，因此可以默认先保留 tar 契约；只有新增对外按需读取需求，或需要在服务端组装成本与客户端升级之间作产品取舍时，才需要进一步选择。
